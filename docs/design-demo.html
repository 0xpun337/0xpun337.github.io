Two runtimes, one pipeline

Tokio owns the I/O. Rayon owns the CPU. Almost nobody talks about the seam between them — which is where all the interesting engineering actually lives.

RustTokioRayon14 min2026

The obvious way to build a high-throughput ingest service in Rust is to put everything on Tokio and call it a day. Read the file with tokio::fs, decrypt it in the same task, encode the rows, hand them to the database driver. One runtime, one mental model, no seams to reason about.

That design has a specific failure mode, and it is not subtle. Decryption and parsing are pure CPU work measured in milliseconds. Drop a millisecond of AES-GCM onto a Tokio worker thread and you have blocked a reactor that was supposed to be servicing hundreds of sockets. Do it on all of them at once and the async runtime stops being a runtime — it becomes an expensive thread pool with a scheduler you can't control.

The rule that falls out of this: a future that computes is a future that lies. It claims it will yield and then doesn't.

So the pipeline runs on two runtimes, deliberately kept apart. Tokio handles everything that waits — directory scans, file reads, the Postgres connection. Rayon handles everything that computes, on a pool whose threads are pinned to specific cores so the scheduler can't migrate a half-finished decrypt across an L2 boundary. Between them sits a bridge: a bounded channel in each direction, and a oneshot to carry each result home.

01 Backpressure is the whole design

Every stage hands work forward through a bounded channel, and the bound is not a tuning detail — it is the mechanism. When the database slows down, the writer's queue fills. When the writer's queue fills, the encoder blocks trying to push into it. That block propagates backwards, stage by stage, until it reaches the scanner, which simply stops claiming new files off disk.

02 The bridge

Handing work from an async task to a Rayon pool is where most implementations quietly go wrong. You cannot await inside Rayon and you must not block inside Tokio, so the bridge has to be explicit — a job goes across on a crossbeam channel, and a oneshot::Sender rides along with it to carry the answer back.

src/core/pipeline.rs
// Async side: hand the CPU job across, then await the answer.
let (tx, rx) = oneshot::channel();

cpu_tx.send(DecodeJob { envelope, reply: tx })?;

// The reactor thread is free the entire time this is pending —
// no AES, no parsing, nothing that computes, ever runs here.
let parsed = rx.await.map_err(|_| Error::CpuPoolGone)??;

// Rayon side: pure CPU, pinned core, zero awareness of async.
pool.spawn(move || {
    let out = decrypt_and_parse(&job.envelope);
    let _ = job.reply.send(out); // receiver dropped = caller cancelled
});

The ?-? on that await is not a typo. The outer one catches the pool died; the inner one catches the job failed. Collapsing them into one error type is how you end up unable to tell a corrupt payload from a panicked worker at three in the morning.
