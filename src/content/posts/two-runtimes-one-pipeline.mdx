The obvious build is everything on Tokio. Read the file with `tokio::fs`, decrypt it in the same task, parse it, hand the rows to the driver. One runtime, one mental model, no seams.

It has a specific failure mode, and it isn't subtle. Decrypt-and-parse is pure CPU work measured in *milliseconds*. Drop a millisecond of AES-GCM onto a Tokio worker and you've blocked a reactor that was meant to be servicing everything else. Do it on every worker at once and the async runtime stops being a runtime — it's an expensive thread pool with a scheduler you don't control.

<p class="note"><b>The rule</b>A future that computes is a future that lies. It promises to yield, then doesn't.</p>

That's easy to assert and easy to hand-wave. So break it yourself. The figure below runs the same workload two ways — hit **Move CPU onto reactor** and watch the middle lane go red:

Nothing about the workload changes when you press that button. The same jobs arrive at the same rate and do the same work. The only difference is *which pool the CPU phase runs on* — and that alone separates a reactor that's 20% busy from one that's pegged.

## <span class="num">01</span> The bridge

So: **two runtimes, deliberately kept apart.** Tokio takes everything that waits. Rayon takes everything that computes, on a pool whose threads are pinned to cores.

<p class="note"><b>Why pin</b>An unpinned worker can be migrated mid-decrypt onto a core whose L2 knows nothing about its working set. You pay for the move twice — once to lose the cache, once to refill it.</p>

You can't `await` inside Rayon and you mustn't block inside Tokio, so the hand-off has to be explicit. The job goes across, and a `oneshot::Sender` rides along to carry the answer back:

```rust
let (cpu_tx, cpu_rx) = oneshot::channel();

cpu_pool().spawn(move || {
    let result = std::panic::catch_unwind(AssertUnwindSafe(|| {
        cpu_job::run(&payload, pre_decrypted)
    }));
    let _ = cpu_tx.send(result);
});

// The reactor thread is free for this entire await. No AES,
// no parsing, nothing that computes ever runs on it.
let outcome = match cpu_rx.await {
    Ok(Ok(outcome)) => outcome,
    Ok(Err(panic)) => { /* see §03 */ }
    Err(_) => return Err(Error::CpuPoolGone),
};
```

Note the `let _ =` on the send. If the caller timed out and dropped its receiver, that send fails — and that's fine. The work is already done and nobody wants it. Treating it as an error means logging a scary line every time a caller walks away.

## <span class="num">02</span> Bridge tasks are not parallelism

Here's the part that took a while to get right. There are roughly **2× physical cores** worth of bridge tasks on the Tokio side. That number looks like a parallelism knob. It isn't.

Every one of those tasks spends essentially all its time parked in `cpu_rx.await`. They aren't doing work — they exist purely to keep the Rayon pool's input queue non-empty. The *real* CPU parallelism is the Rayon pool size, and nothing else.

<p class="note"><b>Tune the right one</b>Adding bridge tasks buys you nothing but memory. Drag the two thread sliders in Fig 1.1 and watch which one actually moves throughput.</p>

The distinction matters because the two knobs fail differently. Too few bridge tasks and the Rayon pool starves between jobs. Too many and you've allocated futures that will never do anything. Too few Rayon threads and cores sit idle. Too many and you're thrashing the caches that pinning was there to protect.

## <span class="num">03</span> A panic is a bug; bad data is not

Wrapping the Rayon job in `catch_unwind` is the kind of thing that gets flagged in review as sloppy. It isn't, and the reason is a distinction worth being strict about.

**Malformed input is an `Err`.** A truncated frame, a bad checksum, a field that doesn't decode — expected, routine, routed to quarantine with a reason attached. Not exceptional.

**A panic is a bug in my code.** An index out of range, an unwrap on a `None`. It means I got something wrong, not that the input was bad.

Opposite problems, so they get opposite treatment:

```rust
Ok(Err(_panic)) => {
    #[cfg(debug_assertions)]
    {
        // Loud in debug and test: re-raise so the bug gets found.
        std::panic::resume_unwind(_panic);
    }
    #[cfg(not(debug_assertions))]
    {
        // Release: isolate this one file, keep the pipeline running.
        metrics::counter!("importer_cpu_panics_total").increment(1);
        tracing::error!(file = %job.path.display(),
            "CPU job panicked — isolating file, pipeline continues");
        // ...quarantine, then carry on with the next file
    }
}
```

In test builds a panic propagates and fails the run, loudly, which is exactly what you want while you're still finding it. In production one bad file lands in `failed/panic` with a metric and an ERROR log, and the rest keep flowing. A service that dies on one malformed input isn't robust — it's brittle with good intentions.

<p class="note"><b>Without the split</b>You get one of two bad outcomes: bugs silently swallowed in test, or an entire run killed in production by a single file.</p>

## <span class="num">04</span> Backpressure is one gate, not many

Every stage hands work forward through a channel bounded at `queue_size`, and admission is governed by a single atomic: `in_flight`. The scanner's budget is `queue_size - in_flight`. When the database slows, the writer's queue fills, the encoder blocks pushing into it, and that block walks backwards until the scanner stops claiming files off disk.

<p class="note"><b>No controller</b>Nothing measures load. Nothing decides. The stall <em>is</em> the signal, and it propagates for free.</p>

Now the interesting exception. The finalizer channels — the ones carrying *delete this file* and *quarantine this file* — are deliberately **unbounded**:

```rust
// Admission control is provided by `in_flight` (bounded by queue_size),
// so these never need to be bounded. Bounded channels would make
// try_send silently drop jobs, leaving files un-finalized and
// in_flight elevated forever.
let (delete_tx, delete_rx) = crossbeam::channel::unbounded::<DeleteJob>();
let (move_tx,   move_rx)   = crossbeam::channel::unbounded::<MoveJob>();
```

This looks like the one place discipline slipped. It's the opposite. `in_flight` already caps how many files exist in the system at once, so these channels have a hard ceiling by construction — unbounded here *cannot* grow without bound. Bounding them anyway would mean `try_send` can fail, and a dropped finalizer job is a file that was successfully written and then never deleted, with `in_flight` never coming back down.

That's the failure I care most about, because of how it presents: no error, no crash. The admission budget ratchets downward over hours until the scanner admits nothing at all, and every log line still looks healthy.

<p class="note"><b>The invariant</b>Every path decrements <code>in_flight</code> exactly once. Not the happy path — <em>every</em> path. File vanished mid-read, hex malformed, decode panicked. Miss one and you've built a slow leak with no symptom.</p>

The structural fix is to route every failure through the same terminal disposition as the success path, so there's exactly one place the decrement can happen. If each error arm has to *remember* to decrement, sooner or later one won't.

## <span class="num">05</span> The drain that must not have a timeout

Graceful shutdown is where crash-safety actually gets decided, and it produced the one comment I'd defend hardest:

```rust
/// We wait UNCONDITIONALLY — there is NO timeout.
```

The reasoning: a batch's domain-table COPYs commit *before* the large, slow `file_details` COPY does. Cut the wait while that one is still committing and those files are left un-finalized — not deleted, not quarantined, still sitting in the source directory. The next run picks them up and duplicates every row they contain.

And an in-progress COPY can't be cancelled anyway. A timeout wouldn't stop the work, only stop you from observing it finish, which is strictly worse than waiting. So the shutdown path awaits the writer, then the finalizers, in that order: the COPYs ack and enqueue their deletes, then those deletes actually run before the runtime is torn down.

<p class="note"><b>The escape hatch</b>A genuinely wedged database still needs an answer. That answer is a second SIGINT, which hard-exits with 130 — an explicit human decision, not a silent timer.</p>

The general shape: when "give up after N seconds" would corrupt data, the timeout isn't a safety feature, it's the bug. Make the impatient path something a human has to consciously choose.
